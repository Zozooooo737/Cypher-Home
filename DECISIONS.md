# DECISIONS : Cypher Home

> Source de vérité des décisions, du périmètre et de l'avancement fonctionnel. Prioritaire sur le cahier des charges (CC).
> Une information vit dans un seul fichier : composants et broches physiques → `CONTEXTE_TECHNIQUE.md` ; étapes, ordre, dépendances, risques et plans B, cases cochées → `PLAN.md` ; tout le reste (périmètre, décisions, fonctions, journal) → ce fichier.

## Périmètre
- Système de mesure + surveillance + consultation à distance. Aucune régulation ni commande d'équipements.
- Échéance : 1er décembre 2026.
- « Contrôle » : ESSENTIEL = contrôle à distance (dashboard) ; IMPORTANT = contrôle sur le prototype via les boutons physiques.
- Scénario de démo : connexion au dashboard, lecture des mesures, activation de la surveillance, détection de présence, délai de 10 s, intrusion avec image et buzzer. Alerte fumée MQ-2 en complément si prête.
- Ordre de réduction du périmètre si le temps manque (du premier retiré au dernier) :
  1. Estimation du nombre de personnes (F8)
  2. Mode batterie et solaire (N7)
  3. Courriel d'alerte (N8)
  4. Mode « respect de l'environnement » et règles de veille écran (F16, F17)
  5. Conservation configurable des données (N9)
  6. Notifications configurables par type (F14), remplacées par une liste fixe
  7. Réglage des consignes sur les boutons de la carte
  8. Menus de l'écran réduits à un affichage fixe
  9. Détection de présence par caméra : photo à la demande seulement (F7)

## Décidé

### Matériel et environnement
- Carte : Arduino UNO R4 WiFi. Firmware en C++ (PlatformIO, VS Code, Windows). Serveur et dashboard en Python. Langages confirmés.
- Tout le matériel du bon de commande est reçu. Caméra : ArduCAM OV5642 (B0068).
- Ressources : multimètre disponible ; BME680 en module Joy-IT à broches ; boîtier 3D conçu et imprimé par l'étudiant (imprimante 3D disponible).
- Alimentation : USB-C = mode principal et sûr ; batterie + cellule photovoltaïque = BONUS, traité après le mode USB-C.
- Bibliothèque caméra (D2) : fork keeeal/ArduCAM-Arduino-Uno-R4, commit 8b276d3 (ArduCAM/Arduino 066a7ea + support UNO R4), copie locale non modifiée dans `firmware/lib/ArduCAM/` (LGPL 2.1), `memorysaver.h` : `OV5642_MINI_5MP_PLUS`. Essayée sur la carte dans les 7 résolutions de 320x240 à 2592x1944.
- Résolution des photos (D9, provisoire) : `OV5642_1024x768` (`config.h`). Retenue d'après les mesures de `docs/tests/camera.md` (67 780 octets et 1 627 ms de transfert à 460800 bauds) ; les résolutions supérieures sont plus lourdes et bloquent la carte plus longtemps pendant l'envoi. À revalider avec le débit Wi-Fi réel en P2.5 (repli : `OV5642_640x480`, une ligne de `config.h`).
- Débit série de test : 460800 bauds (`SERIAL_BAUD` dans `config.h`, à garder égal à `DEFAULT_BAUD` de `serial_monitor.py`). Le plus rapide des trois essayés (115200, 230400, 460800). Canal provisoire de la phase P1, sans lien avec D4.
- BME680 en I2C (D1) : module Joy-IT SEN-BME680, adresse 0x76 (SDO relié à GND), bus I2C partagé avec la caméra (broches SDA/SCL de la carte). Le bus SPI reste réservé à la caméra et à l'écran. Alimentation VIN sur 5V (câblage du manuel Joy-IT) ; 3Vo et CS non connectés. Bibliothèque Adafruit BME680 2.0.6 (Adafruit BusIO 1.17.4, Adafruit Unified Sensor 1.1.15) via lib_deps ; résistance du gaz brute, sans BSEC (pas d'indice IAQ).

### Réseau et serveur
- Serveur et base hébergés en local sur le PC. Le serveur écoute sur `0.0.0.0` ; dashboard à `http://IP_DU_PC:port`, accessible depuis PC et iPhone. Prévoir le pare-feu Windows et le profil réseau privé.
- Wi-Fi : partage de connexion de l'iPhone en 2,4 GHz, « Maximiser la compatibilité » activé. L'IP du PC change à chaque session : une configuration unique dans le firmware est acceptée.

### Méthode
- `PLAN.md` fait référence pour l'ordre des étapes (Px.x).
- Dépôt Git unique à la racine de `CypherHome`, hébergé sur GitHub (visibilité : privé). Convention de commits : voir `docs/CONVENTION_COMMITS.md`.
- Structure du firmware : pas de dossier `tests/`. Un module par composant dans `firmware/src/components/` (`<composant>.h/.cpp` ; noms de fichiers, fonctions et variables en anglais) avec `<composant>_setup()`, les fonctions principales réutilisées par le firmware final et `<composant>_test()`. `firmware/src/self_test.cpp` enchaîne les tests validés (`self_test_run()`) : appelée dans `loop()` pendant le développement, dans `setup()` (une fois) dans la version finale.
- Broches et paramètres : `firmware/include/pins.h` (un bloc par composant listant toutes ses broches, celles sans définition en commentaire, index des broches de la carte en tête ; provisoire tant que D3 est ouverte) et `firmware/include/config.h` (`constexpr`, valeurs par défaut utiles au produit, ajoutées quand le code les utilise, modifiables plus tard depuis le dashboard). Les valeurs propres aux tests restent des constantes locales du `.cpp`. `firmware/include/secrets.h` (ignoré par Git, avec un `secrets.example.h` versionné) est créé au premier secret.
- Sortie série : un script Python unique, `firmware/scripts/serial_monitor.py`, remplace le moniteur PlatformIO ; il affiche le texte et enregistre les images dans `firmware/output/` (ignoré par Git). En phase P1, les images passent par le port USB : transport provisoire de test, sans lien avec D4. Un `.venv` par dossier Python (`firmware/scripts/`, `server/`).
- Fiches de test : une par composant dans `docs/tests/` (modèle `_modele.md`), une page, sans code, rédigées après validation. La fiche garde le câblage testé (daté), `pins.h` le câblage courant, la table D3 validée fait foi.
- Mesures de courant : reportées à la fin du projet (courant total, P1.7) ; la matrice P1.6 utilise les valeurs des datasheets.
- Git : seul l'étudiant commite ; Claude Code fournit les messages de commit (règle dans CLAUDE.md, filet de sécurité dans .claude/settings.json).
- Règles de code : code minimal (CLAUDE.md, « Règles de code ») ; firmware : aucun commentaire dans les .cpp, une ligne par signature de fonction dans les .h (firmware/CLAUDE.md).
- Affichage des tests : bannière, une valeur par ligne alignée par des points (self_test_print(), print_value() côté moniteur), échec = une seule ligne [composant] KO ; règle dans CLAUDE.md.
