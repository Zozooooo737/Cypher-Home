# DECISIONS : Cypher Home

> Source de vérité des décisions, du périmètre et de l'avancement fonctionnel. Prioritaire sur le cahier des charges (CC).
> Une information vit dans un seul fichier : composants et broches physiques → `CONTEXTE_TECHNIQUE.md` ; étapes, ordre, dépendances, risques et plans B, cases cochées → `PLAN.md` ; tout le reste (périmètre, décisions, fonctions, journal) → ce fichier.
> Mis à jour par Claude Code, seulement avec ce que l'étudiant a validé ou demandé (règle dans `CLAUDE.md`).

## Périmètre
- Système de mesure + surveillance + consultation à distance. Aucune régulation ni commande d'équipements.
- Échéance : 1er décembre 2026.
- « Contrôle » : ESSENTIEL = contrôle à distance (dashboard) ; IMPORTANT = contrôle sur le prototype via les boutons physiques.
- Scénario de démo : connexion au dashboard, lecture des mesures, activation de la surveillance, détection de présence, délai de 10 s, intrusion avec image et buzzer. Alerte fumée MQ-2 en complément si prête.
- Ordre de réduction du périmètre si le temps manque (du premier retiré au dernier) :
  1. Estimation du nombre de personnes (F8)
  2. Mode batterie et solaire (N7)
  3. Courriel d'alerte (N8)
  4. Mode « respect de l'environnement » et règles de veille écran (F16, F17)
  5. Conservation configurable des données (N9)
  6. Notifications configurables par type (F14), remplacées par une liste fixe
  7. Réglage des consignes sur les boutons de la carte
  8. Menus de l'écran réduits à un affichage fixe
  9. Détection de présence par caméra : photo à la demande seulement (F7)

## Décidé

### Matériel et environnement
- Carte : Arduino UNO R4 WiFi. Firmware en C++ (PlatformIO, VS Code, Windows). Serveur et dashboard en Python. Langages confirmés.
- Tout le matériel du bon de commande est reçu. Caméra : ArduCAM OV5642 (B0068).
- Ressources : multimètre disponible ; BME680 en module Joy-IT à broches ; boîtier 3D conçu et imprimé par l'étudiant (imprimante 3D disponible).
- Alimentation : USB-C = mode principal et sûr ; batterie + cellule photovoltaïque = BONUS, traité après le mode USB-C.
- Bibliothèque caméra (D2) : fork keeeal/ArduCAM-Arduino-Uno-R4, commit 8b276d3 (ArduCAM/Arduino 066a7ea + support UNO R4), copie locale non modifiée dans `firmware/lib/ArduCAM/` (LGPL 2.1), `memorysaver.h` : `OV5642_MINI_5MP_PLUS`. Essayée sur la carte dans les 7 résolutions de 320x240 à 2592x1944.
- Résolution des photos (D9) : `OV5642_640x480` (`config.h`), retenue d'après P2.5 (`docs/tests/photo_http.md`) : envoi HTTP plafonné vers 10,5 ko/s, carte bloquée pendant l'envoi ; 640x480 : 2,6 à 3,2 s d'envoi, sous la période de mesure de 5 s du CC ; 1024x768 (choix provisoire de P1.1) : 5,3 à 5,9 s ; résolutions supérieures : 7,6 à 28 s.
- Débit série de test : 460800 bauds (`SERIAL_BAUD` dans `config.h`, à garder égal à `DEFAULT_BAUD` de `serial_monitor.py`). Le plus rapide des trois essayés (115200, 230400, 460800). Canal provisoire de la phase P1, sans lien avec D4.
- BME680 en I2C (D1) : module Joy-IT SEN-BME680, adresse 0x76 (SDO relié à GND), bus I2C partagé avec la caméra (broches SDA/SCL de la carte). Le bus SPI reste réservé à la caméra et à l'écran. Alimentation VIN sur 5V (câblage du manuel Joy-IT) ; 3Vo et CS non connectés. Bibliothèque Adafruit BME680 2.0.6 (Adafruit BusIO 1.17.4, Adafruit Unified Sensor 1.1.15) via lib_deps ; résistance du gaz brute, sans BSEC (pas d'indice IAQ).
- MQ-2 (P1.3) : VCC sur 5V, A0 sur A0, D0 non connectée. Lecture de A0 par l'ADC en 14 bits (0 à 16383), moyenne de 16 lectures, sans bibliothèque. Préchauffage fixe de 300 s après la mise sous tension (aucune alerte avant). Alerte au-dessus de 3000 sur 2 échantillons consécutifs, fin sous 2500 (`config.h`). Seuil absolu retenu plutôt qu'un seuil relatif à une référence glissante : sur le log du 2026-11-08, la référence était en retard au passage en prêt et l'alerte restait bloquée après le gaz. Valeurs tirées de deux enregistrements du 2026-11-08 ; si l'air normal dérive vers le seuil, plan B : seuil relatif (PLAN.md, risques).
- Écran ST7735S (P1.4) : bibliothèque Adafruit ST7735 and ST7789 Library 1.12.0 + Adafruit GFX Library 1.13.0 via lib_deps (Adafruit seesaw Library 1.7.9 et SD 1.3.0 figées : déclarées par la bibliothèque, non utilisées). Variante INITR_BLACKTAB (ordre des couleurs correct sur la carte), décalage de 2 colonnes et 1 ligne, rotation 3 (paysage 160x128), réglages dans `config.h`. VCC et BLK sur 3.3V (rétroéclairage toujours allumé). SCL, SDA, RES, DC et CS reliés directement à la carte, sans adaptation de niveaux (choix de l'étudiant, voir la remarque de D3) ; SPI à 4 MHz après l'initialisation (la bibliothèque envoie l'initialisation à sa vitesse par défaut). Bus SPI partagé avec la caméra, CS des deux périphériques à HIGH au début de `setup()`. Broches (D3) : CS D7, RES D8, DC D9.
- LED, boutons, buzzer (P1.5) : 4 LED commandées par un registre à décalage 74HC595 en logiciel (`shiftOut`, MSBFIRST), sans le bus SPI matériel partagé par la caméra et l'écran ; SER A1, RCLK A2, SRCLK A3, OE à GND, SRCLR au 5V ; LED rouge QB (bit 1), bleue QC (bit 2), jaune QD (bit 3), orange QE (bit 4), une résistance de 270 Ω par LED. 5 boutons en `INPUT_PULLUP` (appuyé = LOW), patte A1 sur la broche de la carte et B2 à GND, anti-rebond de 20 ms (`config.h`) : centre D2, droite D3, gauche D4, haut D5, bas D6. Buzzer passif SVM06N sur D0 avec `tone()` (non bloquant dans le cœur Renesas 1.6.0) ; D0 est le RX de `Serial1`, qui ne doit jamais être initialisé.
- Bibliothèque KiCad (P3.1) : hardware/kicad/CypherHome.kicad_sym, bibliothèque spécifique au projet, 15 symboles (un par composant ; LED partagée par les 4 LED, BUTTON par les 5 boutons, R 270 pour les résistances ; AK50X50 = cellule et DFR0579 = module de la SunFlower). Le symbole de la carte a les noms de broches de son modèle d'origine ; correspondances dans CONTEXTE_TECHNIQUE.md. Limites : empreintes non terminées ; plusieurs champs Footprint contiennent du texte libre ou une empreinte absente du projet (Registre, Solaire, Alimentation, LIPO 3,7 V 5000 mAh, 1825910-3:TE_1825910-3, ABX00087:MODULE_ABX00087), avertissements ERC attendus en P3.2 ; broche USB Charge IN absente du symbole DFR0579.
- Interrupteur général (D10) : aucun interrupteur en mode USB-C (le prototype s'éteint en débranchant le câble) ; le DS12A est réservé au mode batterie (P11, BONUS), position exacte à fixer avec D6. Continuité du DS12A vérifiée : Borne 1 et Borne 2 reliées sur ON (2026-11-12), aucune continuité sur OFF (2026-11-13).
- Schéma de câblage (P3.2) : `hardware/kicad/cypher-home.kicad_sch` (une feuille A4) et son export `hardware/kicad/cypher-home.pdf` ; connexions par étiquettes aux noms de `pins.h` (bus : I2C_SDA, I2C_SCL, SPI_MOSI, SPI_MISO, SPI_SCK) ; symboles d'alimentation +5V, +3V3, GND de la bibliothèque standard de KiCad, avec PWR_FLAG (5V et 3.3V fournis par la carte) ; hors schéma : DS12A, LiPo, SunFlower, convertisseur (P11). Revue contre la matrice : `docs/compatibilite.md`.
- Câblage du prototype (P3.3) : câblage complet conforme au schéma et à la table D3, validé le 2026-11-13 ; DS12A et convertisseur Step-Up non câblés (hors schéma : D10, P11) ; fiche : docs/tests/cablage_prototype.md.

### Réseau et serveur
- Serveur et base hébergés en local sur le PC. Le serveur écoute sur `0.0.0.0` ; dashboard à `http://IP_DU_PC:port`, accessible depuis PC et iPhone. Prévoir le pare-feu Windows et le profil réseau privé.
- Wi-Fi : partage de connexion de l'iPhone en 2,4 GHz, « Maximiser la compatibilité » activé. L'IP du PC change à chaque session : une configuration unique dans le firmware est acceptée.
- Wi-Fi de la carte (P2.1) : bibliothèque WiFiS3 fournie par le cœur Renesas 1.6.0 (pas de lib_deps) ; elle parle à l'ESP32-S3 par `Serial2` (UART3, broches internes P501/P502), aucune broche des connecteurs utilisée. Firmware du module Wi-Fi mis à jour de 0.4.1 à 0.6.1 (Arduino IDE 2, Firmware Updater) : avec 0.4.1, les pertes de liaison n'étaient pas toujours vues. SSID et mot de passe dans `secrets.h` (ignoré par Git, modèle `secrets.example.h`). Connexion : 3 tentatives de 10 s au plus (`config.h`), réussie seulement quand le DHCP a donné une IP.
- MQTT (P2.2) : broker Mosquitto 2.0.22 (image `eclipse-mosquitto:2.0.22`, `docker/docker-compose.yml`), port 1883 publié sur toutes les adresses du PC, règle de pare-feu Windows entrante TCP 1883 limitée au profil privé (« Cypher Home - MQTT 1883 ») ; broker arrêté hors des tests. `mosquitto.conf` : `listener 1883` (pas `127.0.0.1` : dans le conteneur, c'est le conteneur lui-même), `allow_anonymous false`, `password_file` (`docker/mosquitto/config/passwd`, ignoré par Git). Un utilisateur par usage : `cypherhome-board` (carte), `cypherhome-server` (serveur). Carte : ArduinoMqttClient 0.1.8 (lib_deps) sur `WiFiClient`, identifiant client `cypherhome-board`, attente de CONNACK 5000 ms (`config.h`), QoS 0, reconnexion avant chaque publication ; IP du broker et identifiants dans `secrets.h`. Serveur : identifiants dans `server/.env` (modèle `server/.env.example`). Pas de TLS (P10.2), pas de droits par sujet. Limites connues : un échec de connexion bloque environ 10 s ; réception par un programme du PC hors du conteneur non testée (P5.2). Cours : `docs/cours/mqtt.md`.
- Envoi HTTP (P2.3, provisoire tant que D4 est ouverte) : `WiFiClient` de WiFiS3, requête `POST /upload HTTP/1.1` écrite à la main (Host, Content-Length, Connection: close), sans bibliothèque HTTP ; corps envoyé par blocs de 2048 octets (`HTTP_BLOCK_BYTES`), lus par une fonction de même signature que `camera_read_block()`, sans tampon de la taille totale. Port 8000, délais de connexion et de réponse de 5 s (`config.h`), IP du PC dans `secrets.h` (`HTTP_SERVER_IP`). Serveur de test `server/test_upload_server.py` (bibliothèque standard Python : Content-Length obligatoire, 512 ko au plus, SHA-256, contrôle d'un motif connu) ; règle de pare-feu Windows entrante TCP 8000 limitée au profil privé (« Cypher Home - HTTP 8000 »). Débit mesuré : environ 10,3 ko/s en blocs de 512 octets et 10,8 ko/s en blocs de 2048, proche du plafond de la liaison série interne carte–ESP32-S3 à 115200 bauds [H]. Mesuré aussi : carte bloquée pendant l'envoi (12,5 s pour 128 ko en blocs de 512 octets) ; serveur coupé en plein envoi : code -3 et non -2. Pas d'authentification ni de TLS (P10). Fiche : `docs/tests/http.md`. Test HTTP (4 tailles) ajouté à `self_test_run()` et validé sur la carte ; 4 tailles gardées jusqu'à P4.1.
- Accès depuis les téléphones (P2.4) : une page servie par le PC (`server/test_page_server.py`, serveur de test provisoire sur 0.0.0.0:8000, bibliothèque standard, sans lien avec D5) s'affiche sur l'iPhone qui émet le partage et sur un second téléphone connecté au partage, par l'IP du PC comme par `<nom du PC>.local` (mDNS). Changement d'IP non testé.
- Outillage serveur (D8) : Docker Desktop (WSL2) pour Mosquitto, testé en P2.2 sans blocage ; repli natif non utilisé ; Docker pour MongoDB à confirmer en P5.1.
- Photo de bout en bout (P2.5) : capture puis `POST /upload` avec le code de P2.3 (Content-Length = longueur lue dans le tampon de la caméra, blocs de 2048 octets lus par `camera_read_block()`) ; `camera_http_test()` dans `self_test_run()` ; banc `camera_http_bench()` (7 résolutions × 3 envois) gardé dans `camera.cpp`, non appelé. Serveur de test : JPEG reconnu par FF D8, FF D9 exigé, limite relevée de 512 ko à 1 Mo, photo enregistrée telle que reçue dans `server/output/` (ignoré par Git), un fil d'exécution par envoi (`ThreadingHTTPServer`) : en un seul fil, un envoi coupé par un redémarrage de la carte bloquait le serveur 30 s (code -3 au premier envoi suivant). Remplissage après FF D9 : jusqu'à 2 049 octets.

### Méthode
- `PLAN.md` fait référence pour l'ordre des étapes (Px.x).
- Dépôt Git unique à la racine de `CypherHome`, hébergé sur GitHub (visibilité : privé). Convention de commits : voir `docs/CONVENTION_COMMITS.md`.
- Structure du firmware : pas de dossier `tests/`. Un module par composant dans `firmware/src/components/` (`<composant>.h/.cpp` ; noms de fichiers, fonctions et variables en anglais) avec `<composant>_setup()`, les fonctions principales réutilisées par le firmware final et `<composant>_test()`. `firmware/src/self_test.cpp` enchaîne les tests validés (`self_test_run()`) : appelée dans `loop()` pendant le développement, dans `setup()` (une fois) dans la version finale.
- Broches et paramètres : `firmware/include/pins.h` (un bloc par composant listant toutes ses broches, celles sans définition en commentaire, index des broches de la carte en tête ; conforme à la table D3) et `firmware/include/config.h` (`constexpr`, valeurs par défaut utiles au produit, ajoutées quand le code les utilise, modifiables plus tard depuis le dashboard). Les valeurs propres aux tests restent des constantes locales du `.cpp`. `firmware/include/secrets.h` (ignoré par Git, avec un `secrets.example.h` versionné) est créé au premier secret.
- Sortie série : un script Python unique, `firmware/scripts/serial_monitor.py`, remplace le moniteur PlatformIO ; il affiche le texte et enregistre les images dans `firmware/output/` (ignoré par Git). En phase P1, les images passent par le port USB : transport provisoire de test, sans lien avec D4. Un `.venv` par dossier Python (`firmware/scripts/`, `server/`).
- Fiches de test : une par composant dans `docs/tests/` (modèle `_modele.md`), une page, sans code, rédigées après validation. La fiche garde le câblage testé (daté), `pins.h` le câblage courant, la table D3 validée fait foi.
- Mesures de courant : reportées à la fin du projet (courant total, P1.7) ; la matrice P1.6 utilise les valeurs des datasheets.
- Git : seul l'étudiant commite ; Claude Code fournit les messages de commit (règle dans CLAUDE.md, filet de sécurité dans .claude/settings.json).
- Règles de code : code minimal (CLAUDE.md, « Règles de code ») ; firmware : aucun commentaire dans les .cpp, une ligne par signature de fonction dans les .h (firmware/CLAUDE.md).
- Affichage des tests : bannière, une valeur par ligne alignée par des points (self_test_print(), print_value() côté moniteur), échec = une seule ligne [composant] KO ; règle dans CLAUDE.md.
- Exception d'affichage (mqtt) : en cas d'échec, `[mqtt] KO` est suivi d'une ligne `[mqtt] code erreur` (code `connectError()` d'ArduinoMqttClient), choisie par l'étudiant pour distinguer « broker injoignable » et « identifiants refusés ».
- Exception d'affichage (http) : en cas d'échec, `[http] KO` est suivi d'une ligne `[http] code erreur` (-1 connexion impossible, -2 envoi interrompu, -3 pas de réponse, sinon code HTTP reçu), validée par l'étudiant sur le modèle de [mqtt].
- Documentation : `docs/tests/` = fiches de test d'une page sans code ; `docs/cours/` = cours et rapports longs de l'étudiant, avec explications (un fichier par sujet). Pour MQTT, le cours `docs/cours/mqtt.md` tient lieu de fiche.
